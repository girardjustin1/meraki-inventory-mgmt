# Supabase: database for Meraki Inventory

| File | What it is |
| --- | --- |
| `migrations/0001_init.sql` | The base schema: tables, enums, triggers, grants and row-level security. |
| `migrations/0002_access_and_invites.sql` | Admin and User access levels, the policies reworked to the permission model, and invites. |
| `seed.sql` | The two locations and the seven vendors. No staff, no stock, no client data. |
| `seed-catalog.sql` | Generated by `tools/seed/build-seed-sql.ts`: the catalogue, Lynnfield stock levels and the imported 2026 orders. Git-ignored. |

Nothing in this folder has been applied to a real Supabase project yet. Both migrations and both seed files were run end to end in an in-memory Postgres (PGlite) with stand-ins for Supabase's roles and `auth.jwt()`, and the policies and triggers were exercised there (see "How this was checked"). Treat the first run against a real project as the real test.

## 1. Apply the schema

Run the files in this order: `0001_init.sql`, `0002_access_and_invites.sql`, then `seed.sql`, then `seed-catalog.sql`. `0002` also applies cleanly to a database that already has data and staff in it: existing owners become admins and everyone else becomes a user.

### With the dashboard

1. Create a project at supabase.com. Pick the region closest to Massachusetts (`us-east-1`, N. Virginia).
2. Open **SQL Editor**, paste the contents of `migrations/0001_init.sql`, and run it. Then do the same with `migrations/0002_access_and_invites.sql`.
3. Paste and run `seed.sql`.
4. `seed-catalog.sql` is about 600 KB, which is large for the editor. Use the CLI or `psql` for that one (below).

### With the CLI

```bash
# once per machine
brew install supabase/tap/supabase
supabase login

# from the repo root
supabase init                              # only if supabase/config.toml does not exist yet
supabase link --project-ref <project-ref>  # the ref is in the project URL
supabase db push --dry-run                 # shows that 0001 and 0002 would be applied
supabase db push                           # applies them, in order

supabase db query --linked -f supabase/seed.sql

npx tsx tools/seed/build-seed-sql.ts       # writes supabase/seed-catalog.sql
supabase db query --linked -f supabase/seed-catalog.sql
```

`psql` works too, with the connection string from **Project Settings > Database**:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 --single-transaction -f supabase/migrations/0001_init.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 --single-transaction -f supabase/migrations/0002_access_and_invites.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/seed.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/seed-catalog.sql
```

Both seed files use `on conflict do nothing`, so running them again changes nothing. Each migration is written to run once, and should run as one transaction so a failure leaves nothing half-applied: `supabase db push` does that by itself and `--single-transaction` does it for `psql`. In the SQL editor, put `begin;` on the first line and `commit;` on the last.

Expected row counts after seeding: 2 locations, 7 vendors, 1,747 items, 7 shelves, 1,747 stock levels, 22 purchase orders, 385 purchase order lines (34 of them not matched to a catalogue item), 0 stock movements.

## 2. Connect Clerk as a third-party auth provider

Staff sign in with Clerk. Supabase is told to trust Clerk's session tokens, so every request from the app arrives in Postgres with the Clerk user's id in `auth.jwt()->>'sub'`. This is Supabase's native third-party auth integration. It does not use a JWT template and it does not share the Supabase JWT secret with Clerk (that older approach was deprecated in April 2025).

1. In Clerk, open [dashboard.clerk.com/setup/supabase](https://dashboard.clerk.com/setup/supabase), choose the application and instance, and activate the Supabase integration. This adds `"role": "authenticated"` to every session token. Copy the **Clerk domain** it shows (for example `clerk.inventory.example.com`, or `something.clerk.accounts.dev` for a development instance).
2. In Supabase, open **Authentication > Sign In / Providers > Third-Party Auth**, choose **Add provider > Clerk**, and paste the Clerk domain.
3. In Clerk, open **Sessions > Customize session token** and add the claims that accepting an invite reads (see "Invites" below):

   ```json
   {
     "email": "{{user.primary_email_address}}",
     "email_verified": "{{user.email_verified}}",
     "name": "{{user.full_name}}"
   }
   ```

4. Nothing else. The app passes the Clerk session token on every request (`apps/web/lib/supabase/server.ts`).

Do this once per Clerk instance: the development instance and the production instance have different domains. For a local Supabase stack, the equivalent is in `supabase/config.toml`:

```toml
[auth.third_party.clerk]
enabled = true
domain = "something.clerk.accounts.dev"
```

Leave Supabase's own email sign-in switched off (**Authentication > Sign In / Providers**). Nobody should be able to create a Supabase Auth user; identity comes only from Clerk.

### Create the first owner

A Clerk user with no row in `profiles` passes no policy and sees nothing. Profiles are created by accepting an invite, and only an admin can send one, so the first admin has to be made by hand. After the owner has signed in with Google once (they will land on the "you need an invite" page, which is expected), run this in the SQL editor, using the user id shown on their page in the Clerk dashboard:

```sql
insert into public.profiles (id, email, name, role)
values ('user_xxxxxxxxxxxxxxxxxxxxxxxx', 'owner@example.com', 'Owner name', 'owner')
on conflict (id) do update set role = 'owner', active = true;
```

An owner is always an admin (the database fills that in), and admins see every location, so they need no `profile_locations` rows. From here on, everyone else is invited from inside the app. If the owner has set `CLERK_DELETE_UNINVITED_USERS=true`, do this before they leave the "you need an invite" page, or have them sign in again afterwards and use the new user id.

It is worth making a second admin straight away (invite them with Admin access). Separation of duties applies to admins too, so an order built by the only admin could not be approved by anyone.

## 3. What the policies do

Row-level security is on for all 22 tables. A request passes through two layers:

- **Grants** decide which operations and which columns the `authenticated` role may touch at all.
- **Policies** decide which rows.

`anon` (no session) has no privileges on anything. The service role (the secret key, used only by the server) bypasses policies, but not CHECK constraints and not the append-only triggers.

Every policy is written with a few helper functions, which live in the `app` schema (not exposed through the Data API):

| Function | Answers |
| --- | --- |
| `app.auth_user_id()` | Who is calling? The `sub` claim of the Clerk token. |
| `app.auth_role()` | What is their role? Read from `profiles`; null if they have no active profile. |
| `app.auth_is_admin()` | Are they an active admin? |
| `app.can('orders.receive')` | May they do this? Admins: always. Users: when their role grants the permission. Unknown permission names raise an error. |
| `app.is_manager()` | Manager-level: an admin, or a user whose role is manager. |
| `app.has_location(location_id)` | May they act at this location? Admins: always. Everyone else: only with a `profile_locations` row. |

### Access levels and permissions

`profiles.access_level` is `admin` or `user`. An admin can do everything at every location. A user gets what their role grants, at their own locations. Owners are always admins. The model is defined once, in `packages/ui/engine/permissions.ts`; `app.role_grants()` is the database's copy of `ROLE_GRANTS` from that file, and `npm run test:db` fails if the two differ. Change both together.

Where each permission is enforced:

| Permission | Granted to users with role | Enforced by |
| --- | --- | --- |
| `stock.view` | manager, front desk, technician | `stock_levels`, `shelves`, `locations` select: `has_location()`. Catalogue: any active staff. |
| `stock.count` | manager, front desk, technician | `count_sessions`, `count_lines`: the assignee, or manager-level. |
| `usage.log` | manager, front desk, technician | `stock_movements` insert, type `use`, at their location. |
| `stock.adjust` | manager | `stock_movements` insert, `adjust` and transfers: `is_manager()`. Par levels: the stock-level trigger. |
| `counts.schedule` | manager | `count_sessions`, `count_lines` insert and delete: `is_manager()`. |
| `counts.approve` | manager | The count trigger: `is_manager()`, and never a count they performed. |
| `orders.view` | manager, front desk | `purchase_orders` select: `can('orders.view')`. |
| `orders.create` | manager | `purchase_orders` and lines insert, update, delete: `is_manager()`. Includes submitting, placing and closing an order. |
| `orders.approve` | nobody: admins only | The order trigger: `can('orders.approve')`, and never an order they created. |
| `orders.receive` | manager, front desk | `stock_movements` insert, type `receive`, and `item_barcodes` insert: `can('orders.receive')`. Never an order they created. |
| `flags.view` | manager | `flags`, `flag_events` select: `is_manager()` at the location. |
| `flags.resolve` | manager | `flags` update and the flag trigger: `is_manager()`, and never a flag about themselves. |
| `costs.view` | manager | `item_costs`, `purchase_order_line_costs`: `is_manager()`. |
| `reports.view` | manager | No table of its own. Reports are computed from the ledger, orders and costs: manager-level callers read their locations' ledger; other staff read only their own entries. |
| `digests.view` | manager | `digest_runs` select: admins all, `can('digests.view')` at their locations. |
| `activity.view` | manager | `audit_log` select: admins all, `can('activity.view')` at their locations. Rows with no location (roles, invites, settings) are for admins only. |
| `team.manage` | nobody: admins only | `profiles` update, `profile_locations` insert and delete, everything on `invites`. |
| `settings.manage` | nobody: admins only | `settings`, `notification_rules`, `locations` and `vendors` writes. |
| `locations.all` | nobody: admins only | `has_location()` is true everywhere for admins. |

Two things changed for people who had access under `0001` alone. Approving an order now takes an admin (a second manager used to be enough). Adding and editing vendors now takes an admin (managers used to be able to).

Guard rails on roles and access levels:

| Rule | How it is enforced |
| --- | --- |
| Nobody changes their own role or access level, or deactivates themselves. | Profile trigger. |
| Only an admin changes anyone's role, access level or locations. | Update policy on `profiles`, insert and delete policies on `profile_locations`, and the profile trigger. |
| Owners are always admins. | CHECK constraint `profiles_owner_is_admin`, and the profile trigger, which fills the value in on insert and refuses to lower it. |
| The last active admin cannot be demoted, deactivated or deleted. | Trigger `profiles_last_admin`. It applies to every writer, including the service role and the SQL editor, and takes a lock so two simultaneous demotions cannot both pass. |

### Policy groups

"Manager-level" below means an admin, or a user whose role is manager. Admins act at every location.

| Group | Tables | Rule |
| --- | --- | --- |
| A. Location scoping | `locations`, `shelves`, `stock_levels` | Staff read rows for their own locations. Admins read all. Manager-level callers edit par levels and shelves; other staff can only raise a reorder request. Admins rename locations. |
| B. Catalogue | `vendors`, `items`, `item_barcodes` | Every active staff member reads. Manager-level callers write items. Admins write vendors. Anyone who can receive can attach a barcode. Items are never deleted, only discontinued. |
| C. Costs | `item_costs`, `purchase_order_line_costs` | Manager-level only. See "Costs" below. |
| D. The ledger | `stock_movements` | Insert only, by duty: `receive` needs `orders.receive`; any active staff member can insert `use` at their location; only manager-level callers can insert `adjust` and transfers; nobody can insert `count` (the approval trigger does). Manager-level callers read their locations' ledger; other staff read only their own entries. No update, no delete. |
| E. Purchasing | `purchase_orders`, `purchase_order_lines` | Manager-level callers create and edit orders at their locations. Approving takes an admin. Front desk can read orders, in order to receive. Technicians cannot see orders. |
| F. Counting | `count_sessions`, `count_lines` | The assignee and manager-level callers see a count. The assignee enters quantities. Only a manager-level caller approves. |
| G. Flags | `flags`, `flag_events` | Manager-level only, at their locations. Front desk and technicians never see flags, because a flag can be about them. Flags are created by the scheduled scan, not by users. |
| H. People and settings | `profiles`, `profile_locations`, `notification_rules`, `settings`, `invites` | Everyone reads their own profile. Managers read staff at their locations. Admins read and edit everyone, assign locations, change settings and manage invites. |
| I. History | `audit_log`, `digest_runs` | Read-only. Admins read all; managers read rows for their locations. |

### Separation of duties

These are enforced in the database, so they hold whichever screen, script or API call makes the change. They bind admins exactly as they bind everyone else: being an admin never lets a person check their own work.

| Rule | How it is enforced |
| --- | --- |
| You cannot approve a purchase order you created. | CHECK constraint `purchase_orders_approver_is_not_creator` (applies to every writer, including the service role), plus the workflow trigger, which sets `approved_by` from the token so it cannot be supplied by the client. |
| You cannot receive a purchase order you created. | The ledger trigger refuses a `receive` movement when the movement's user is the order's creator. |
| You cannot approve a count you performed. | CHECK constraint `count_sessions_approver_did_not_count` (approver is not the assignee or the submitter), plus the workflow trigger, which also checks who counted each line. |
| You cannot close a flag about your own activity. | CHECK constraint `flags_subject_cannot_resolve`, plus the flag trigger. |
| Nobody changes their own role or access level. | Profile trigger. |

Consequences to plan for. Orders are approved by an admin who did not build them, so if admins build orders the business needs at least two admins. Counts are approved by a manager-level person who did not count, so each location needs someone other than the counter who can approve.

Identity fields are never taken from the client. `user_id` and `occurred_at` on a movement, `created_by` and `approved_by` on an order, `counted_by` and `expected` on a count line, and `resolved_by` on a flag are all set by triggers from the token.

### The ledger

- `stock_movements` and `audit_log` are append-only three ways: the `authenticated` and service roles have no UPDATE, DELETE or TRUNCATE privilege; there is no UPDATE or DELETE policy; and a trigger raises on any attempt, including from the SQL editor.
- Every inserted movement is applied to `stock_levels.on_hand` by a trigger, in the same transaction, and the new total is written to `balance_after`. Signed-in users have no UPDATE privilege on `on_hand`, so writing a movement is the only way to change stock.
- A `receive` movement that names an order line also adds to that line's `qty_received` and moves the order to `partially_received` or `received`.
- Approving a count posts one `count` movement per counted line, with `delta = counted - expected`.
- CHECK constraints: a reason is required; the reason must belong to the movement type; the sign of `delta` must match the type; an adjustment of 3 or more units needs a note.

### Costs: why there is no `unit_cost` column on `items`

Only owners and managers may see costs. Row-level security filters rows, not columns, and column-level GRANTs are per database role. Every signed-in user arrives as the same `authenticated` role, so a GRANT cannot tell a manager from a technician. A cost column on `items` would be readable by all staff or by none.

So the cost is in its own table, `item_costs`, whose policies admit owners and managers only. The view `items_with_cost` joins it back and runs with the caller's rights (`security_invoker`), so a technician reading the view gets every item with `unit_cost` null. `purchase_order_line_costs` and `purchase_order_lines_with_cost` do the same for order lines. Read the views when you want the `Item` and `PurchaseOrderLine` shapes from `packages/ui/data/types.ts`.

### PIN columns: the column-level approach

Three columns on `profiles` (`pin_hash`, `failed_pin_attempts`, `pin_locked_until`) are different: no signed-in user needs to read them, ever. So they are simply left out of the column-level SELECT and UPDATE grants. Only the server reads and writes them, with the service role, in `apps/web/app/api/pin/route.ts`. Two side effects:

- `select *` on `profiles` is refused for signed-in users. Name the columns.
- The generated column `has_pin` is readable, so the app can show whether a PIN is set.

### Invites

An invite is the only way a profile comes to exist (apart from the first owner). `apps/web/lib/invites.ts` and the routes under `apps/web/app/api/invites/` drive it; the rules are here.

**The token is never stored.** An invite link carries a random token. `invites.token_hash` holds only its SHA-256 hash (lower-case hex of the UTF-8 token). The app shows the token once, when the invite is created or resent. `token_hash` is not in the column-level SELECT grant, so no signed-in user can read it, admins included, and it is stripped from the audit log.

| Column | Notes |
| --- | --- |
| `email` | Lower-cased. Null means an open link. |
| `role`, `access_level`, `location_ids` | What accepting it grants. Never `owner`. A user invite needs at least one location. An open link cannot be `admin`. |
| `invited_by`, `created_at` | Stamped from the caller's token by the trigger. |
| `token_issued_at`, `resend_count` | When the current token was issued. Equal to `created_at` until the invite is resent. |
| `expires_at` | At most 48 hours after `token_issued_at` for an open link, 168 hours (7 days) for an email invite. Defaults to the maximum. |
| `accepted_at`, `accepted_by` | Set only by `accept_invite()`. Not writable by clients. |
| `revoked_at`, `revoked_by` | Set when an admin revokes. `revoked_by` comes from the token. |
| `clerk_invitation_id` | Reserved, unused. See `docs/architecture.md`, "Clerk and sign-up". |

Status is derived, not stored: `accepted` if `accepted_at` is set, else `revoked` if `revoked_at` is set, else `expired` if `expires_at` has passed, else `pending`. Read it from the view `invites_with_status`, which is every column except the hash, plus `status`.

What can happen to an invite after it is created, and nothing else: it is accepted, it is revoked, or it is resent (a new `token_hash`, which restarts the expiry and kills the old link). An accepted or revoked invite is final. Who it is for and what it grants never change.

Policies: admins (`team.manage`) select, insert and update. There is no delete. Nobody else can read invites: not managers, not the person invited. `anon` has no privilege on the table at all.

**Two functions in `public`, each granted to exactly one role:**

| Function | Who can run it | What it does |
| --- | --- | --- |
| `invite_preview(token)` | `service_role` only | What the accept screen may show someone holding a link, before they sign in. The browser never calls it; the server does, behind `GET /api/invites/preview`. Returns no row for an unknown token. For a pending invite: the inviter's name, role, access level, location names, note, expiry, whether it is email-bound, the address masked as `n••••@example.com`, and the greeting name. For any other status: the status, the inviter's name and the expiry only. Never an id, a full address or the hash, and it never looks anything up by email. |
| `accept_invite(token)` | `authenticated` only | Accepts for the signed-in Clerk user. One transaction: locks the invite row, checks status and expiry, checks the email for an email invite, creates the profile and `profile_locations` (or reactivates a deactivated profile with what this invite grants), marks the invite accepted. The audit triggers record each step. Returns `{ ok, ... }` or `{ ok: false, error }`. |

A Supabase project grants new tables and functions in `public` to `anon` and `authenticated` by default. The migration revokes all of that for the invites table, the view and both functions, then grants exactly what is listed here. After applying, check **Advisors > Security**.

**Identity for `accept_invite()` comes only from the verified Clerk token:** `sub` for the user id, and the custom claims `email`, `email_verified` and `name` (set up in section 2). The caller passes nothing but the token.

- No `email` claim: every acceptance is refused with `email_claim_missing`, open links included, and nothing is written. A profile needs an address, and the token is the only trustworthy source.
- `email_verified` present and not true: refused with `email_not_verified`. Absent: allowed.
- Email invite and the addresses differ: `email_mismatch`.
- The caller already has an active profile: `already_member`. Nothing changes. (Otherwise an owner opening a technician's link would become a technician.)
- The address belongs to a different Clerk user's profile: `email_in_use`. This happens when a former member's Clerk account was deleted and recreated. Fix it by hand: either reactivate the old profile, or change the old row's email in the SQL editor. Deactivate former staff; do not delete their Clerk accounts.
- Two people submitting the same link at once: the second waits on the row lock, then gets `already_accepted`. The same person submitting twice gets `ok` both times.

### Audit log

A trigger writes one `audit_log` row for every insert, update and delete on orders, order lines, counts, count lines, flags and items, and on the configuration that changes what the controls mean: costs, profiles (roles and access levels), location assignments, invites, vendors, settings, notification rules, and par levels on `stock_levels`. `on_hand` changes are not duplicated there, because the ledger is already that record. `pin_hash` and `token_hash` are never copied into the log.

`actor_id` is the Clerk user id from the token. It is null when the change came from the server (service role) or the SQL editor.

`events` names what happened, for the changes people ask about by name. `old_row` and `new_row` still hold the full before and after.

| Event | Written when |
| --- | --- |
| `profile.created` | A profile is inserted (an invite was accepted, or the first owner was added by hand). |
| `profile.role_changed`, `profile.access_changed` | The role or the access level changes. One row can carry both. |
| `profile.deactivated`, `profile.reactivated` | `active` changes. |
| `profile.location_added`, `profile.location_removed` | A `profile_locations` row is added or removed. |
| `invite.created`, `invite.resent`, `invite.revoked`, `invite.accepted` | The invite lifecycle. For `invite.accepted` the actor is the person who accepted. |

```sql
-- who changed whose access, newest first
select at, actor_id, row_id as profile, old_row ->> 'access_level' as was, new_row ->> 'access_level' as now
from public.audit_log
where 'profile.access_changed' = any (events)
order by at desc;
```

Rows about people, invites and settings have no location, so only admins can read them.

## 4. Things this schema does not do

- **Blind counts are a screen-level control.** `count_sessions.blind` tells the app not to show the expected quantity. The database cannot hide it, because staff can read `stock_levels.on_hand` for their location.
- **Thresholds in `settings` are stored but not applied yet.** `detectFlags()` in `packages/ui/engine/flags.ts` reads a constant. It needs a thresholds argument before per-location settings take effect.
- **No opening-balance movements.** `seed-catalog.sql` writes `stock_levels.on_hand` directly. The ledger starts at go-live and the first count sets the real numbers.
- **No storage bucket.** `items.image_url` holds a URL. If item photos are to be uploaded, create a bucket and its policies in a later migration.
- **Negative on-hand is allowed.** It means usage was logged against stock that was never received or counted. Blocking it would stop staff logging real usage.
- **Expired invites are not swept up.** They stay in `invites` with status `expired` until someone resends or revokes them. There is no cleanup job.
- **Notification rules name roles, not access levels.** `order-approval` goes to owners, but under `0002` any admin can approve an order. An admin who is not an owner is not emailed.
- **No rate limit on token lookups.** The database makes them possible only through the server; limiting them is done in front of the app (Vercel Firewall on `/api/invites/preview`).

## 5. How this was checked

Without Docker or `psql` on the development machine, the files were run in PGlite (Postgres compiled to WebAssembly) with stand-ins for the `anon`, `authenticated` and `service_role` roles and for `auth.jwt()`. Run it with `npm run test:db` from the repo root.

- `0001_init.sql` applies cleanly; `seed.sql` and `seed-catalog.sql` each apply twice with no error and no duplicate rows.
- `0002_access_and_invites.sql` is applied on top of that, to a database that already has staff in it, and the existing owner comes out as an admin.
- 350 checks pass, run as different users by setting the role and the JWT claims.
  - The 140 written for `0001` run unchanged against the `0002` rules: location scoping, cost hiding, PIN column privacy, each ledger insert rule, the CHECK constraints, the full order flow, the full count flow, flag handling, each separation-of-duties rule (trigger and constraint), append-only enforcement, and the audit log. One fixture changed: the "second manager" who approves the order in those checks is now an admin, because approving an order takes one.
  - 210 for `0002`: the database's permission matrix against `permissions.ts`; an admin and a user tried against every permission, including an admin whose role is technician and who has no location rows; separation of duties binding admins; the guard rails (own role, own access level, owners, the last admin, as a user, as postgres and as the service role); and the invite lifecycle: create, the constraints, preview (pending, accepted, expired, revoked, unknown), accept, missing email claim, wrong email, unverified email, expired, revoked, resent, double acceptance, open links, admin invites, returning staff, who can call which function, and the audit events.

Not checked: behaviour on a real Supabase project (role attributes, default privileges, PostgREST, real Clerk tokens and their custom claims). Two people accepting the same invite at the same instant cannot be run in PGlite, which has one connection; the row lock is there and is checked for by reading the function, not by racing it. After applying, open **Advisors > Security** in the Supabase dashboard and review anything it reports.
