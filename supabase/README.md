# Supabase: database for Meraki Inventory

| File | What it is |
| --- | --- |
| `migrations/0001_init.sql` | The whole schema: tables, enums, triggers, grants and row-level security. |
| `seed.sql` | The two locations and the seven vendors. No staff, no stock, no client data. |
| `seed-catalog.sql` | Generated by `tools/seed/build-seed-sql.ts`: the catalogue, Lynnfield stock levels and the imported 2026 orders. Git-ignored. |

Nothing in this folder has been applied to a real Supabase project yet. The migration and both seed files were run end to end in an in-memory Postgres (PGlite) with stand-ins for Supabase's roles and `auth.jwt()`, and the policies and triggers were exercised there (see "How this was checked"). Treat the first run against a real project as the real test.

## 1. Apply the schema

Run the files in this order: `0001_init.sql`, then `seed.sql`, then `seed-catalog.sql`.

### With the dashboard

1. Create a project at supabase.com. Pick the region closest to Massachusetts (`us-east-1`, N. Virginia).
2. Open **SQL Editor**, paste the contents of `migrations/0001_init.sql`, and run it.
3. Paste and run `seed.sql`.
4. `seed-catalog.sql` is about 600 KB, which is large for the editor. Use the CLI or `psql` for that one (below).

### With the CLI

```bash
# once per machine
brew install supabase/tap/supabase
supabase login

# from the repo root
supabase init                              # only if supabase/config.toml does not exist yet
supabase link --project-ref <project-ref>  # the ref is in the project URL
supabase db push --dry-run                 # shows that 0001_init.sql would be applied
supabase db push                           # applies it

supabase db query --linked -f supabase/seed.sql

npx tsx tools/seed/build-seed-sql.ts       # writes supabase/seed-catalog.sql
supabase db query --linked -f supabase/seed-catalog.sql
```

`psql` works too, with the connection string from **Project Settings > Database**:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/migrations/0001_init.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/seed.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/seed-catalog.sql
```

Both seed files use `on conflict do nothing`, so running them again changes nothing. The migration is written to run once on an empty project.

Expected row counts after seeding: 2 locations, 7 vendors, 1,747 items, 7 shelves, 1,747 stock levels, 22 purchase orders, 385 purchase order lines (34 of them not matched to a catalogue item), 0 stock movements.

## 2. Connect Clerk as a third-party auth provider

Staff sign in with Clerk. Supabase is told to trust Clerk's session tokens, so every request from the app arrives in Postgres with the Clerk user's id in `auth.jwt()->>'sub'`. This is Supabase's native third-party auth integration. It does not use a JWT template and it does not share the Supabase JWT secret with Clerk (that older approach was deprecated in April 2025).

1. In Clerk, open [dashboard.clerk.com/setup/supabase](https://dashboard.clerk.com/setup/supabase), choose the application and instance, and activate the Supabase integration. This adds `"role": "authenticated"` to every session token. Copy the **Clerk domain** it shows (for example `clerk.inventory.example.com`, or `something.clerk.accounts.dev` for a development instance).
2. In Supabase, open **Authentication > Sign In / Providers > Third-Party Auth**, choose **Add provider > Clerk**, and paste the Clerk domain.
3. Nothing else. The app passes the Clerk session token on every request (`apps/web/lib/supabase/server.ts`).

Do this once per Clerk instance: the development instance and the production instance have different domains. For a local Supabase stack, the equivalent is in `supabase/config.toml`:

```toml
[auth.third_party.clerk]
enabled = true
domain = "something.clerk.accounts.dev"
```

Leave Supabase's own email sign-in switched off (**Authentication > Sign In / Providers**). Nobody should be able to create a Supabase Auth user; identity comes only from Clerk.

### Create the first owner

A Clerk user with no row in `profiles` passes no policy and sees nothing. The app creates profile rows on first sign-in from the role in the Clerk invitation (see `apps/web/README.md`), but the first owner has to exist before anyone can be invited from inside the app. After the owner has signed in once, run this in the SQL editor, using the user id shown on their page in the Clerk dashboard:

```sql
insert into public.profiles (id, email, name, role)
values ('user_xxxxxxxxxxxxxxxxxxxxxxxx', 'owner@example.com', 'Owner name', 'owner')
on conflict (id) do update set role = 'owner', active = true;
```

Owners see every location, so they need no `profile_locations` rows.

## 3. What the policies do

Row-level security is on for all 21 tables. A request passes through two layers:

- **Grants** decide which operations and which columns the `authenticated` role may touch at all.
- **Policies** decide which rows.

`anon` (no session) has no privileges on anything. The service role (the secret key, used only by the server) bypasses policies, but not CHECK constraints and not the append-only triggers.

Every policy is written with three helper functions, which live in the `app` schema (not exposed through the Data API):

| Function | Answers |
| --- | --- |
| `app.auth_user_id()` | Who is calling? The `sub` claim of the Clerk token. |
| `app.auth_role()` | What is their role? Read from `profiles`; null if they have no active profile. |
| `app.has_location(location_id)` | May they act at this location? Owners: always. Everyone else: only with a `profile_locations` row. |

### Policy groups

| Group | Tables | Rule |
| --- | --- | --- |
| A. Location scoping | `locations`, `shelves`, `stock_levels` | Staff read rows for their own locations. Owners read all. Managers and owners edit par levels and shelves; other staff can only raise a reorder request. |
| B. Catalogue | `vendors`, `items`, `item_barcodes` | Every active staff member reads. Managers and owners write. Front desk can attach a barcode. Items are never deleted, only discontinued. |
| C. Costs | `item_costs`, `purchase_order_line_costs` | Owners and managers only. See "Costs" below. |
| D. The ledger | `stock_movements` | Insert only, by duty: front desk, managers and owners can insert `receive`; technicians and everyone else can insert `use`; only managers and owners can insert `adjust` and transfers; nobody can insert `count` (the approval trigger does). Managers read their locations' ledger; other staff read only their own entries. No update, no delete. |
| E. Purchasing | `purchase_orders`, `purchase_order_lines` | Managers and owners create and edit orders at their locations. Front desk can read them, in order to receive. Technicians cannot see orders. |
| F. Counting | `count_sessions`, `count_lines` | The assignee and managers see a count. The assignee enters quantities. Only a manager or owner approves. |
| G. Flags | `flags`, `flag_events` | Managers and owners only, at their locations. Front desk and technicians never see flags, because a flag can be about them. Flags are created by the scheduled scan, not by users. |
| H. People and settings | `profiles`, `profile_locations`, `notification_rules`, `settings` | Everyone reads their own profile. Managers read staff at their locations. Owners read and edit everyone, assign locations, and change settings. |
| I. History | `audit_log`, `digest_runs` | Read-only. Owners read all; managers read rows for their locations. |

### Separation of duties

These are enforced in the database, so they hold whichever screen, script or API call makes the change.

| Rule | How it is enforced |
| --- | --- |
| You cannot approve a purchase order you created. | CHECK constraint `purchase_orders_approver_is_not_creator` (applies to every writer, including the service role), plus the workflow trigger, which sets `approved_by` from the token so it cannot be supplied by the client. |
| You cannot receive a purchase order you created. | The ledger trigger refuses a `receive` movement when the movement's user is the order's creator. |
| You cannot approve a count you performed. | CHECK constraint `count_sessions_approver_did_not_count` (approver is not the assignee or the submitter), plus the workflow trigger, which also checks who counted each line. |
| You cannot close a flag about your own activity. | CHECK constraint `flags_subject_cannot_resolve`, plus the flag trigger. |
| Nobody changes their own role. | Profile trigger. |

A consequence to plan for: each location needs at least two people who can approve (for example the owner and one manager). An order created by the only manager has to be approved by the owner.

Identity fields are never taken from the client. `user_id` and `occurred_at` on a movement, `created_by` and `approved_by` on an order, `counted_by` and `expected` on a count line, and `resolved_by` on a flag are all set by triggers from the token.

### The ledger

- `stock_movements` and `audit_log` are append-only three ways: the `authenticated` and service roles have no UPDATE, DELETE or TRUNCATE privilege; there is no UPDATE or DELETE policy; and a trigger raises on any attempt, including from the SQL editor.
- Every inserted movement is applied to `stock_levels.on_hand` by a trigger, in the same transaction, and the new total is written to `balance_after`. Signed-in users have no UPDATE privilege on `on_hand`, so writing a movement is the only way to change stock.
- A `receive` movement that names an order line also adds to that line's `qty_received` and moves the order to `partially_received` or `received`.
- Approving a count posts one `count` movement per counted line, with `delta = counted - expected`.
- CHECK constraints: a reason is required; the reason must belong to the movement type; the sign of `delta` must match the type; an adjustment of 3 or more units needs a note.

### Costs: why there is no `unit_cost` column on `items`

Only owners and managers may see costs. Row-level security filters rows, not columns, and column-level GRANTs are per database role. Every signed-in user arrives as the same `authenticated` role, so a GRANT cannot tell a manager from a technician. A cost column on `items` would be readable by all staff or by none.

So the cost is in its own table, `item_costs`, whose policies admit owners and managers only. The view `items_with_cost` joins it back and runs with the caller's rights (`security_invoker`), so a technician reading the view gets every item with `unit_cost` null. `purchase_order_line_costs` and `purchase_order_lines_with_cost` do the same for order lines. Read the views when you want the `Item` and `PurchaseOrderLine` shapes from `packages/ui/data/types.ts`.

### PIN columns: the column-level approach

Three columns on `profiles` (`pin_hash`, `failed_pin_attempts`, `pin_locked_until`) are different: no signed-in user needs to read them, ever. So they are simply left out of the column-level SELECT and UPDATE grants. Only the server reads and writes them, with the service role, in `apps/web/app/api/pin/route.ts`. Two side effects:

- `select *` on `profiles` is refused for signed-in users. Name the columns.
- The generated column `has_pin` is readable, so the app can show whether a PIN is set.

### Audit log

A trigger writes one `audit_log` row for every insert, update and delete on orders, order lines, counts, count lines, flags and items, and on the configuration that changes what the controls mean: costs, profiles (roles), location assignments, vendors, settings, notification rules, and par levels on `stock_levels`. `on_hand` changes are not duplicated there, because the ledger is already that record. `pin_hash` is never copied into the log.

`actor_id` is the Clerk user id from the token. It is null when the change came from the server (service role) or the SQL editor.

## 4. Things this schema does not do

- **Blind counts are a screen-level control.** `count_sessions.blind` tells the app not to show the expected quantity. The database cannot hide it, because staff can read `stock_levels.on_hand` for their location.
- **Thresholds in `settings` are stored but not applied yet.** `detectFlags()` in `packages/ui/engine/flags.ts` reads a constant. It needs a thresholds argument before per-location settings take effect.
- **No opening-balance movements.** `seed-catalog.sql` writes `stock_levels.on_hand` directly. The ledger starts at go-live and the first count sets the real numbers.
- **No storage bucket.** `items.image_url` holds a URL. If item photos are to be uploaded, create a bucket and its policies in a later migration.
- **Negative on-hand is allowed.** It means usage was logged against stock that was never received or counted. Blocking it would stop staff logging real usage.

## 5. How this was checked

Without Docker or `psql` on the development machine, the files were run in PGlite (Postgres compiled to WebAssembly) with stand-ins for the `anon`, `authenticated` and `service_role` roles and for `auth.jwt()`:

- `0001_init.sql` applies cleanly; `seed.sql` and `seed-catalog.sql` each apply twice with no error and no duplicate rows.
- 140 checks pass, run as different users by setting the role and the JWT claims: location scoping, cost hiding, PIN column privacy, each ledger insert rule, the CHECK constraints, the full order flow (create, approve by a second person, send, receive by front desk), the full count flow (count, submit, approve, movements posted), flag handling, each separation-of-duties rule (trigger and constraint), append-only enforcement, and the audit log.

Not checked: behaviour on a real Supabase project (role attributes, PostgREST, real Clerk tokens). After applying, open **Advisors > Security** in the Supabase dashboard and review anything it reports.
